Overall Session Notes / Next Steps

17:20 — Section 4 (BLE Connection Test) results — filled in after testing (2 ESP32-S3 boards, one running the IMU rig as a BLE peripheral, one as a bare BLE central "console" stand-in):

Advertising working? Yes — central found the peripheral's advertised service UUID within ~70ms of starting a scan, consistently across multiple runs.

Successful connection from central? Yes — full handshake completes reliably every time: connect → MTU exchange (negotiated 64 bytes) → service discovery → characteristic discovery → CCCD write (subscribe) → notifications flowing within ~1 second of connect.

If multiple boards available — simultaneous connections tested? No — only tested 1 peripheral to 1 central (both boards available were used in those roles). Multi-peripheral (4-to-1) simultaneous connection load not yet tested.

Any dropped connections / cross-talk observed? Zero packet drops across two runs totaling ~6500+ sequence-number-verified samples. One full disconnect/reconnect cycle was deliberately tested (reset the peripheral mid-session): central detected the disconnect immediately, auto-resumed scanning, found and reconnected to the peripheral, and resubscribed — full recovery in well under 1 second, no manual intervention. No cross-talk possible to observe with only one peripheral present, but the central's service-UUID filter is the mechanism that would prevent it in a multi-device environment.

Achieved connection interval: 50.0ms (NimBLE's negotiated default — not forced shorter). This directly answers the "realistic minimum connection interval" open question from the Wireless Protocol Selection / MCU Selection docs — 50ms was what NimBLE settled on unprompted; forcing a shorter interval (BLE supports down to 7.5ms) would need explicit connection parameters, not left to default negotiation.

Full data rate / throughput findings written up separately — see the new "BLE Data Rate & Throughput Findings" page in Prototype.
