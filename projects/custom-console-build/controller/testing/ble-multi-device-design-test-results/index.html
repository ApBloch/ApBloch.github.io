BLE Multi-Device Design & Test Results

Design reference for the BLE link between controller boards and the console, plus real measured results from a live 4-peripheral→1-central test. Supersedes the investigation trail in BLE Data Rate & Throughput Findings (that page documents how we got here; this page documents where we landed).

Topology

Star topology matching the final product: up to 4 BLE peripherals (controllers), each maintaining exactly 1 connection, to a single BLE central (console/receiver). This was chosen specifically because NimBLE supports multi-connection central natively.

Wire packet format (27 bytes, packed)

typedef struct __attribute__((packed)) {
    uint16_t buttons;       // bitmask (2B)
    int16_t  ax, ay, az;    // accel, raw register counts, +-2g FS (6B)
    int16_t  gx, gy, gz;    // gyro, raw register counts, +-2000dps FS (6B)
    uint16_t seq;           // sequence number, drop detection (2B)
    uint8_t  reserved[11];  // unused, zeroed
} ble_imu_packet_t;  // = 27 bytes exactly

_Static_assert(sizeof(ble_imu_packet_t) == 27, "must be exactly 27 bytes");

Raw int16 register counts on the wire (not converted floats) — matches the packet-size budget in Worksheet - Controller/IMU Packet Design field-for-field, with seq as the one addition for this test's own drop counting.

Connection parameters

  • Connection interval: 20ms (negotiated/observed on every connection in testing)
  • ATT MTU: 128 (via CONFIG_BT_NIMBLE_ATT_PREFERRED_MTU=128) — far more than the 27B payload needs; MTU was never actually the bottleneck
  • CONFIG_BT_NIMBLE_MAX_CONNECTIONS=4 on the central; =1 on each peripheral

Update rate: genuine 50Hz, unbatched

Each board's main loop runs at 100Hz (vTaskDelayUntil); a single, real ble_imu_packet_t is sent via one ble_gatts_notify_custom() call on every 2nd tick → a true 50Hz notify rate, one sample per packet, no batching.

Why 50Hz and not 100Hz: empirical testing found a per-connection notify() ceiling of ~73–76 calls/sec on this ESP32-S3/NimBLE stack, independent of payload size, connection interval, compiler optimization, or splitting across characteristics. This lines up with widely-reported ~15ms/66.6Hz BLE notification floors on iOS centrals. 50Hz was chosen as a genuine (not batched) rate with real margin under that ceiling, rather than pushing 100Hz and quietly merging samples into bigger packets.

Central-side multi-connection design

Central tracks up to MAX_PERIPHERALS=4 peripheral slots in an array (peripheral_slot_t), keyed by conn_handle in every GAP/GATT callback. It scans continuously while under the connection cap, and on each new connection: allocates a slot, exchanges MTU, discovers the service/characteristic, subscribes (CCCD write), and resumes scanning if slots remain. On disconnect, the slot is freed and scanning resumes automatically. Per-slot drop detection compares each packet's seq against the last seen value.

Throughput & reliability (measured, 2026-08-12)

4 physical boards connected simultaneously: Board A (real IMU, ESP32-S3), two dummy-peripheral ESP32-S3 boards, and one dummy-peripheral classic ESP32 (different chip family, same NimBLE protocol — confirms the design is chip-agnostic across the ESP32/S3 family). All four showed itvl=20.0ms mtu=128.

Clean 33.6s measurement window, taken directly from the central's own per-slot counters:

1Board A — real IMU168050.00/s0 (0.00%)

Combined throughput: 200 packets/sec across 4 simultaneous connections (4 × 50Hz, exactly on target), zero dropped packets in the window. Cumulative session totals at time of capture: 48,322 packets received across all 4 slots, 0 dropped all-time. Cross-checked on the sender side too — Board A's own heartbeat reported notify_ok=14368 notify_fail=0, confirming the zero-drop result isn't just the receiver failing to notice drops.

Conclusion: the design comfortably supports the full 4-controller star topology at the target 50Hz per device with no observed packet loss, and does so identically whether the peripheral is an ESP32-S3 or a classic ESP32.

Receiver CPU & memory headroom (measured, 4/4 connected)

Added FreeRTOS runtime-stats reporting (CONFIG_FREERTOS_USE_TRACE_FACILITY + CONFIG_FREERTOS_GENERATE_RUN_TIME_STATS) to the receiver and captured vTaskGetRunTimeStats() plus heap readings every 5s while all 4 peripheral slots were connected and streaming at ~50Hz each. Figures below are stable, converged samples taken ~10–40s after boot.

TaskCore / role%CPU
IDLE1core 1 idle~99%
IDLE0core 0 idle~87–91%
mainheartbeat / logging / status loop~4–5%
nimble_hostNimBLE host stack~1–4%
btControllerBLE controller~2%
esp_timer / ipc0 / ipc1system<1% each

Core 1 is essentially untouched (~99% idle) — nothing was pinned there in this test. Core 0, which runs the main app task plus the whole NimBLE stack (host + controller) for all 4 simultaneous connections, is still ~87–91% idle — total BLE + status-logging load is only ~9–13% of one core, even scanning continuously and juggling 4 connections at once.

Heap: 278,648 bytes free, holding rock steady (min_ever_free equal to current free) across the whole capture window — no leak, and a large RAM margin left over.

Conclusion: this board has substantial CPU (especially core 1, entirely free) and RAM headroom for whatever else the final console needs to do — UI, haptics, USB/host-side reporting, etc. — well beyond just running the BLE receive side.

Open item from this same capture: one peripheral connected but never completed CCCD subscription (stuck at "discovering..." for the full 40s window) after the receiver's reboot-triggered mass-reconnect of all 4 boards at once — the other 3 subscribed and started streaming within ~1s. Didn't affect the CPU/heap numbers (that peripheral was just idle from the receiver's side), but worth another look if it recurs outside of a simultaneous-reconnect scenario.

Firmware layout

  • ESP_IMU_Test/ — Board A, real IMU peripheral (SPI + BLE)
  • ble_console_test/ — Board B, multi-connection central/console
  • ble_dummy_peripheral/ — stand-in peripheral (no sensor hardware), builds for both esp32s3 (default build dir) and classic esp32 (build.esp32 dir) targets from the same source

ble_imu_packet.h is duplicated byte-identical across all three projects (no shared-lib setup for this prototype phase).
