SPI Bring-Up: MISO Signal Integrity Bug (LSM6DSV320X)

Bug hit during IMU bring-up on the breadboard (2026-08-09), diagnosed and fixed with a series resistor. Documenting so we don't re-diagnose this from scratch next time.

Symptom

  • WHO_AM_I read back 0x64 instead of the correct 0x73 (per the ST datasheet, this register is fixed-value and should never read anything else).
  • Reads alone looked "stable" (same wrong value every time), so it wasn't obviously a wiring fault at first glance.
  • The moment any control register was written (e.g. CTRL1/CTRL2 to bring the accel/gyro out of power-down), the ESP32's SPI bus permanently hung on the very next transaction — not a crash, a genuine lock-up. The task watchdog fired twice (5s, 10s) and then went completely silent forever, confirmed via backtrace: stuck inside spi_device_polling_transmit/spi_device_polling_end, which uses an infinite wait internally, so a truly stalled SPI hardware transaction never returns.

Root cause

Signal integrity on the SPI lines over breadboard jumper wires — specifically the SDO → MISO line. Not a firmware bug, not a bad register value, not a wiring mistake in the usual sense (continuity was fine). This is a documented issue on ST's own community forum for this exact chip + adapter board on breadboard/jumper connections — other users hit the identical 0x64 vs 0x73 symptom. One forum user's exact finding: making the SDO→MISO jumper a double/longer wire changed the value to the correct 0x73, and the oscilloscope waveform looked completely different — a classic reflection/ringing signature, not a logic-level fault.

Fix

Added a ~100Ω resistor in series on the SDO → ESP32 GPIO13 (MISO) line, placed at the master (ESP32) end. This damps the reflections caused by the unterminated breadboard jumper acting like a small transmission line at SPI clock edge rates.

Result: WHO_AM_I reads a clean, stable 0x73 across hundreds of reads, and the CTRL register writes that used to hang now land correctly (verified via register readback) with the sensor streaming normal data and zero watchdog resets over an extended test run.

If you ever see the same symptom again on a different signal/board: try the same 100Ω series resistor trick on that line first. General ST guidance for SPI signal integrity on jumper/breadboard runs is 51–100Ω in series on all lines at the master, so if one resistor doesn't fully clear it, add resistors to SCLK/MOSI/CS too before assuming something else is wrong.

Sources

  • ST Community: "lsm6dsv320x WHO_AM_i" — the thread describing the exact same 0x64-instead-of-0x73 symptom on breadboard jumpers
  • Same thread, page 2 — more user reports, including the "longer wire fixed it" data point
  • LSM6DSV320X datasheet (DS14623 Rev 1) — used to verify the actual register map (WHO_AM_I, CTRL1/CTRL2, the high-g accelerometer channel, STATUS_REG) instead of guessing from a related chip family

Firmware, in plain terms

Full code: ESP_IMU_Test/main/main.c on the dev machine (ESP-IDF project, not Arduino). What it does, roughly in order:

  1. Sets up two separate serial buses: SPI to talk to the IMU (GPIO10-13), and a second UART — UART1 on GPIO17 — just for streaming data out, kept separate from the USB/console UART so logs and data don't collide.
  2. Reads WHO_AM_I as a first handshake check — if the chip doesn't answer with the right ID, it stops and logs an error instead of pushing forward blind.
  3. Configures three sensor channels by writing a few control registers: the normal (low-g) accelerometer and gyroscope at 120 Hz, plus the IMU's high-g accelerometer channel at 480 Hz / ±320g — that last one is the channel that won't clip on a hard throw, which is the whole reason this chip is in the prototype.
  4. Reads back every register it just wrote, to catch a corrupted write immediately rather than trusting it silently (this is what would have caught the resistor bug faster, in hindsight).
  5. Loops forever: checks a status register to see if new data is ready, reads it when it is, and sends it out as a simple line of text (comma-separated numbers) over the UART1 wire. Also prints one line a second to the normal USB console, so readings can be sanity-checked without any extra hardware.

Everything streamed is raw sensor counts, not converted to g's or degrees/sec — that conversion is a simple multiply against a datasheet constant, left for whenever the data actually needs to be in physical units.
